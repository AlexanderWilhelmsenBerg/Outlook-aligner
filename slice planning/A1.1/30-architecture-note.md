## Precise implementation contract for Agent 40

### 1. Baseline used to generate the lockfile

Use exactly:

- **Node.js `24.20.0`**
- **npm `11.19.0`**

This is the repository-documented LTS baseline and therefore the authoritative toolchain for creating the first real `package-lock.json`.

The existing `package.json` `engines.node` compatibility declaration (`>=24.0.0`) does not need to be narrowed merely to create the lockfile. Compatibility metadata and the repository's deterministic lockfile-generation/CI baseline serve different purposes.

### 2. Generate the lockfile with npm; never synthesize it

From a clean worktree at `web/calendar`, with Node `24.20.0` / npm `11.19.0` active, run the real npm resolver against the current manifest:

```text
npm install --ignore-scripts
```

That command must create `web/calendar/package-lock.json` from the existing `package.json` and exact declared dependency versions. Do not hand-edit, generate, script, copy, or fabricate lockfile dependency data.

After generation, review the manifest/lockfile diff. The operation must not intentionally change any declared dependency version. In particular, keep Vite `8.3.0`.

A `npm install --package-lock-only --ignore-scripts` generation is also technically valid if Agent 40 prefers not to populate `node_modules` at that step, but the resulting lockfile must still be generated by npm `11.19.0` from the current manifest and then proven by a clean `npm ci` install. There is no architecture reason to prefer hand-editing or another package manager.

### 3. Pin CI to the lockfile-generation Node baseline

In `.github/workflows/ci.yml`, change the frontend job from floating Node `24` to exact **`24.20.0`**.

Do not add a second package manager or dependency-version manager. Node `24.20.0` is documented by this repository as carrying npm `11.19.0`; CI should verify the effective versions before installation (at minimum print `node --version` and `npm --version`, and fail if they are not `v24.20.0` / `11.19.0`). If setup-node's exact Node distribution does not actually provide the documented npm version, that discrepancy is a blocker to resolve explicitly rather than silently generating the lock with another npm version.

No additional `.nvmrc`, `.node-version`, `packageManager` field, or global npm replacement is required for this slice unless implementation evidence shows the documented baseline cannot otherwise be reproduced. Avoid adding redundant version mechanisms just for decoration.

### 4. Deterministic install command

Replace frontend verification installs with:

```text
npm ci --ignore-scripts
```

Keep `--ignore-scripts` for A1.1. It is part of the current repository's install posture, and the existing frontend has already been built under ignored lifecycle scripts. A1.1 is not the place to broaden dependency execution privileges.

If `npm ci --ignore-scripts` fails because a dependency truly requires a lifecycle script, Agent 40 must stop and report that evidence to Agent 30/Agent 00; do not quietly drop `--ignore-scripts` as an implementation convenience.

### 5. Preserve all current frontend quality gates

The frontend CI job must still execute, after deterministic installation:

```text

npm run lint

npm run build
npm audit --omit=dev --audit-level=high
```

Do not weaken or remove any of these gates. Do not add a dependency-upgrade sweep to make the audit easier; if the exact current locked graph creates a new high/critical production audit finding, report it as a blocker rather than opportunistically changing unrelated versions inside A1.1.
